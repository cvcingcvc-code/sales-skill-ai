# 单店商品销售与客服 MVP 需求

本文定义产品从通用客服演示走向“商家可配置商品销售客服”的最小需求与验收边界。这里描述的是目标和验收标准，不代表功能已经实现。现有能力以 [README](../README.md) 和真实验收记录为准。

## 1. 产品目标

让一家普通商家在自己的 Windows、macOS、Linux 电脑或受控服务器上配置一个店铺，维护商品和审核过的经营资料，通过网站访客页面处理售前商品咨询。系统有明确依据时才建议答复；资料不足、规则不清、风险较高或模型不可用时，交给人工处理。

首个 MVP 不要求自动完成交易。它验证“商家配置资料 → 顾客咨询 → 有依据地建议答复或转人工 → 管理员处理”的闭环。

## 2. 使用角色与核心流程

### 商家/管理员

1. 在本机启动服务并通过管理员认证。
2. 创建和维护商品、价格、销售条件、发货说明、售后政策及 FAQ。
3. 维护实际经营平台的规则资料，填写规则来源、适用平台/类目、生效日期或版本，并审核后启用。
4. 查看访客问题、系统建议、所用知识依据、规则检查结果及人工接管队列。
5. 对投诉、退款、价格/库存冲突、规则不确定和知识缺口进行人工回复。

### 顾客

1. 查看商家公开的在售商品。
2. 询问商品特点、适用条件、价格及已录入的售前政策。
3. 收到基于商家审核资料的答复，或看到系统说明需要人工确认。

## 3. 商家资料需求

商品资料至少应能表达：

- 商品名称、商家内部编号（可选）、描述、规格/选项和上下架状态。
- 当前价格、币种、价格适用条件及最后核对时间；没有可靠实时库存时必须明确标示库存信息未验证。
- 适用对象/条件、限制、发货方式与预计时效（仅能录入商家确认的表述）。
- 退换/售后规则及对应的知识条目。

知识资料至少应支持 FAQ、商品说明、售后政策、经营规则和平台规则，并保存标题、正文、来源/适用商品、适用范围、版本或生效时间、审核状态及更新时间。未审核或已过期资料不得作为自动答复依据。出现相互冲突的价格或政策时应提示人工确认。

这些字段是需求定义，需先与现有数据模型核对；本文件不要求为了字段齐全而重写现有架构。

## 4. 回复与人工边界

- 自动建议只能使用当前店铺已审核且适用的商品与知识资料。
- 答复应能在后台追溯到使用的商品/知识依据；依据缺失时不得补猜。
- 未覆盖问题、互相矛盾或过期资料、价格/库存无法确认、投诉、退款、配送争议、特殊优惠、法律/合规判断都应转人工。
- 模型超时、不可用、预算耗尽或配置错误时，应安全降级并创建可见的人工待办，不得返回伪造的模型答复。
- 顾客消息、商品描述和知识正文均是数据，不具有系统指令权限。
- 首个 MVP 不执行下单、付款、库存扣减、退款、改价或自动发货。购买意向最多展示商家审核过的人工购买指引或无资金流的模拟流程。

## 5. 平台规则资料与发送前检查

平台规则作为商家可维护的知识类型之一，但“收录规则”与“自动阻止不合规内容”是两项不同能力。若进入实际发送拦截验收，应具备以下要求：

- 每项规则记录平台/渠道、来源链接或文件、适用类目/场景、规则版本/生效日期、审核人/审核状态和最后核对日期。
- 规则可区分明确禁止、满足特定条件才可使用、允许但必须附带说明、仅供人工参考等类别；不能把所有规则退化为一份无上下文词表。
- 对拟发送回复执行检查。明确命中禁止规则时阻止发送并转人工；条件不足、规则冲突或版本过期时要求人工复核。
- 记录命中规则、触发片段、处理结果和人工复核结果，以便审计和修正规则。
- 覆盖上下文样例：真正违规的承诺、对禁用表达的引用/解释、否定语境、同义说法和无关普通用词，评估误拦与漏拦。
- 规则知识只代表商家录入和审核的范围，不保证覆盖平台全部政策，也不构成法律意见或平台合规保证。规则更新需由商家重新核对和启用。

首轮演示可以先展示规则录入与人工审核；在发送前拦截未经过专门测试之前，不得宣传自动合规审查已经可用。

## 6. 隐私与凭据

- 模型 API Key 和管理员令牌只保存在后端私密配置中，不得进入访客浏览器、页面脚本、截图、日志或 Git。
- 访客留资遵循明确同意、最少收集、可撤回/删除和既定保留期限；商品及规则管理不应要求录入无关客户个人信息。
- 商家应能区分本地 SQLite 数据位置、备份与删除范围。
- 演示和验收优先使用虚构资料；真实商家试用需事先授权并限制资料范围。

## 7. 最小验收场景

通过标准必须来自实际部署环境和可复核证据。Mock、规则回复或 Codex 辅助人工回复不能算作真实模型通过。

1. **商品知识内咨询：**真实模型答复中的价格/条件与商家审核数据一致，后台可查看使用依据。
2. **知识缺口：**询问未录入的库存、优惠或发货承诺时，模型不编造，访客进入人工流程。
3. **模型不可用：**停止模型服务或使用受控故障条件，访客获得清晰降级结果且后台出现待处理接管。
4. **平台规则：**明确禁止的拟发送内容被拦截；条件性规则资料缺失或过期时要求人工确认；中性讨论违禁表达的对照样例不应仅因关键词出现而一律误拦。
5. **商家配置：**管理员添加、审核、修改、停用商品和知识，访客只能读取公开有效商品。
6. **持久化：**重启 API 与工作台后，商品、审核状态、规则版本和接管记录仍正确。
7. **凭据与权限：**未授权管理员请求被拒绝，访客响应和静态资源中没有管理员令牌或模型 API Key。

验收记录应注明环境、分支/提交、Provider 与真实模型名、脱敏请求/响应、耗时、场景结果及日志；无法运行应标记 `BLOCKED`，未请求模型应标记 `NOT_RUN`。

## 8. 先做与暂不做

**先做：**单店商品与知识维护、资料审核、真实模型商品问答、未知问题转人工、模型故障降级、规则资料维护及明确边界的发送前检查、重启持久化。

**暂不做：**真实支付、自动订单创建/修改、库存扣减、退款、自动发货、多平台消息聚合、多租户 SaaS、任意平台规则自动同步和合规保证。

完成上述最小闭环后，再基于商家反馈决定是否接入具体电商或消息平台。任何平台集成都需逐个平台核对授权方式、审核政策、数据范围和维护成本。
