# 本轮优化计划与后续推进

先改善资料命中、商品与政策的对应关系、无效请求的预算计数和持续回归，再依据真实咨询数据决定下一步。继续沿用现有 FastAPI、Streamlit、SQLite 和模型网关，不以整仓重构或引入向量库作为前提。

本轮运行配置保持 `MODEL_ENABLED=false`、`LLM_PROVIDER=ollama`，不安装模型服务、不下载权重、不执行真实模型请求。离线 Mock 回归只验证软件合约；真实模型效果为 `NOT_RUN`，暂停时真实验收为 `BLOCKED / disabled`。

## 本轮改动与验收门槛

以下描述本轮实现目标与应验证的行为，不是测试完成声明。实际命令、结果、提交 SHA 和远端 CI 状态由本轮交付记录补充，不能由计划推定。

| 优化 | 用户收益 | 验收门槛 |
| --- | --- | --- |
| 知识先按问题相关性排序，再截取候选 | 商品有多份文档时，真正相关的政策不会因原列表顺序而落在前 8 条之外 | 构造超过候选上限的干扰文档，将目标文档排在原列表后方；相关文档仍能入选，结果稳定，停用知识和下架商品资料仍不能进入候选 |
| 后端校验商品与政策关联，并在回复标明适用商品 | 比较多款产品时，避免把 A 商品的售后政策误用于 B 商品 | 有关联的政策必须通过后端商品范围和有效状态校验；跨商品误选转人工，不能仅凭模型 ID 选择展示。合法比较应明确各政策属于哪款；通用政策不伪装成特定商品承诺 |
| 客服在预留日预算前调用无网络的 `validate_request` | 明知超长或无效的请求无需发送 HTTP，也不会消耗共享模型日额度 | 商品、知识、历史或系统消息造成超限时，HTTP 请求数和客服预算次数/token/金额计数保持不变；有效请求仍先预留再调用、再按有效用量结算；不自动裁剪上下文 |
| 加入严格离线 GitHub Actions 与安全计数报告 | 每次同步代码后自动发现回归，避免“没发现测试却显示成功” | Python 3.12、Node 22、锁定 Python 依赖及 `pip check`；零项测试必失败，`--strict` 模式任何跳过或预期失败必失败，测试失败/异常或尝试外连必失败；JSON 仅含固定计数与状态，真实模型验证始终 `NOT_RUN` |

资料排序改变候选优先级，不等于模型回答质量已经提高。关联校验是后端约束，不能只写成提示词。`validate_request` 复用网关配置、暂停和消息长度校验，不创建 HTTP/SDK 客户端，不把估算值当作 Provider 实际 token 用量；消息记录和必要人工转接仍可以保存。

上下文只能按完整消息和完整候选资料项缩减：保留系统信任边界、当前问题和最高优先级商品/知识，先移除最旧历史，再移除较低优先级资料；不截断字符串。若当前问题和核心证据仍超限，则在模型调用和额度预留前转人工。真实调用已经发出后发生的失败、缺用量或崩溃，仍按现有保守预算机制处理；前置拒绝不扣日额度不意味着所有失败请求都退款。客服每日预算也不覆盖旧销售训练的全部日调用。

## 按独立阶段交付

1. 完成资料排序和关联约束，运行对应回归与原功能回归。
2. 完成网关无网络校验及预算调用顺序，覆盖超限边界、零 HTTP、零预算消耗和正常结算。
3. 完成离线 runner 与 GitHub Actions，覆盖零项发现、跳过、失败、异常、外连及安全 JSON 输出。
4. 汇总完整离线回归和明确标识的合成演示，检查差异与敏感文件，再按 [DEVELOPMENT.md](DEVELOPMENT.md) 提交并推送当前隔离开发分支。

每阶段先测试，再明确暂存相关文件、提交并同步 GitHub。推送成功仅证明远端分支已接收代码；GitHub Actions 是否运行和通过，需要核对同一提交的远端结果。未获得结果时记录待验证，不宣称 CI 通过。V2.1 阶段分支为 `codex/workbench-quality-v2.1`，本次后续改动单独在 `codex/retrieval-budget-v2.2` 开发，不自动合并主分支或部署生产。

## 2026-10-19 本轮进展

已实现路线 1 与 2：新增 30 条固定合成检索回归，覆盖相似名称、双商品比较、后排目标文档、无答案、停用/下架资料、关联政策及错误价格诱导；记录商品与知识 Recall@k，并检查无答案误召回。基准只衡量确定性检索，不代表真实客户或模型准确率。客服明确人民币上限会在模型调用前过滤候选，并在调用后重新读取当前价格；边界价包含在预算内，金额近似/区间/币种不明以及没有合规商品时转人工，不调用模型。代码和结果见 [ACCEPTANCE_REPORT_V2_2.md](ACCEPTANCE_REPORT_V2_2.md)。

离线回归通过不代表 DeepSeek 或 Ollama 的端到端调用已通过；模型仍关闭，真实验证 `NOT_RUN`。V2.3 按下方优先级继续。

## 2026-10-20 本轮进展

已实现路线 3：资料选择器在无网络前置校验失败时，先移除整条最旧历史，再移除较低排序的完整知识/商品候选，并同步删去已移除商品的关联知识；保留当前问题、系统提示及最高排序核心候选。核心候选仍无法放入上下文时转人工，不调用模型、不预留日额度。新增 `SUPPORT_MODEL_MAX_OUTPUT_TOKENS`，默认 512，单次 Provider 输出与客服日额度预留都使用不超过通用上限的同一数值。新旧销售训练保持原输出配置。

本地合成回归结果待本轮运行后写入 [ACCEPTANCE_REPORT_V2_3.md](ACCEPTANCE_REPORT_V2_3.md)；真实模型仍暂停，不把 Mock 结果称为模型验收。

| 优先级 | 下一步 | 收益与验收方式 |
| --- | --- | --- |
| 1 | 建立不少于 30 条固定检索基准 | 已有 30 条合成固定用例，按人工标注资料 ID 统计商品与知识 Recall@k 及无答案误召回；数据和结果见 V2.2 报告。仅代表确定性检索，不代表模型回答准确率 |
| 2 | 客户预算金额的推荐约束 | 已将明确人民币上限与实际商品价格做后端筛选和推理后复核；未知币种、模糊金额及无符合商品转人工，见 V2.2 报告 |
| 3 | 有界上下文打包与客服专用输出上限 | 已按完整资料项打包并限制客服选择器输出；严格回归超长资料、多轮历史、信任边界与额度预留，见 V2.3 验收记录 |
| 4 | 本地 JSON schema 与真实模型实测 | 确定硬件、模型和 Ollama 版本后，再评估其受支持的结构化输出方式；在后端继续校验 ID、类型和权限。实测格式合规率、引用、拒答、延迟与资源占用；当前不安装/下载，也不保证某模型满足要求 |
| 5 | SQLite 一致备份恢复、权限与按规模优化 | 先演练在线一致备份或停写快照，恢复到隔离目录核对关联记录和约束，覆盖 WAL 与备份访问权限。索引、分页和查询优化由记录量、查询计划和延迟证据驱动，不先替换数据库 |
| 上线前门槛 | 公网小流量验收 | 验证 HTTPS、私有后台、准确来源限流、持久化、备份恢复、保留/删除、人工值守及费用边界；本地模型机离线能够转人工。使用已审核商家资料完成真实问答后，才开展受控小流量访问 |

检索 Recall@k 按“前 k 条命中的期望资料数 / 全部期望资料数”计算；期望为空的题目单独计无答案误召回，避免空分母。基准需要完整标注相关范围，并固定数据、查询和排序条件。检索指标不能替代真实模型、业务政策或安全验收。

硬件未确定前只做软件和离线基准；需要模型时再按 [LOCAL_MODEL_DEPLOYMENT.md](LOCAL_MODEL_DEPLOYMENT.md) 部署并独立验收。现有运维边界见 [DEPLOYMENT.md](DEPLOYMENT.md)，工作流与权限见 [ARCHITECTURE.md](ARCHITECTURE.md)。本轮完成上述范围后停止，不自行扩展外呼、支付、微调、多智能体或前端重写。
