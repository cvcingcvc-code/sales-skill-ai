# AI 店铺智能客服工作台：中文产品路线图

## 产品定位

目标是让普通个人商家、小型店铺和销售团队从 GitHub 获取项目后，能够在自己的 Windows、macOS、Linux 电脑或受控服务器上逐步部署店铺客服，而不要求具备专业 AI 开发经验。

商家自行维护并审核商品、价格、常见问题、售后规则、发货说明和经营政策，也可维护其实际经营平台的规则资料。顾客通过网页文字客服咨询时，系统应检索商家知识，再交由已配置且可用的模型辅助回答；资料不足、无法确认、平台规则命中、投诉、退款或其他特殊情况交由人工。部署者应理解数据存在哪里、模型如何连接、费用如何产生、服务故障如何处理。

模型选择遵循明确配置：

- **本地模型**：例如由 Ollama 在商家自己的设备运行，降低对云服务的依赖；实际可用性受设备、模型、资源与网络配置影响。
- **云端模型 API**：例如 DeepSeek，由商家自己申请并安全保管 `DEEPSEEK_API_KEY`。
- **其他模型**：按真实用户需求逐个评估、实现适配器并测试；现有配置或适配器都不代表任意模型或任意 API Key 可以直接使用。

Codex 是开发和任务执行工具，不是产品中自动常驻的客服服务。网站自动客服必须有可用模型运行环境，或有经商家授权的外部模型 API。此前演示中 Codex 辅助人工拟写、管理员再发送的流程，不能作为网站自动 AI 回复的证明。

## S1：文档与产品定位

**目标：** 让 GitHub 访问者能用普通语言理解产品用途、已实现能力、使用边界和长期方向。

**交付内容：**

- 中文 README：首页说明适用用户、演示场景、安装入口、安全要求、模型状态和真实验收方式。
- 中文路线图：区分当前 MVP、单店自托管验证和后续真实商家试用。
- 保留现有演示截图、证据、模型关闭说明、隐私与部署安全警告。

**完成判断：** 新访问者能找到首次启动步骤，并能区分当前人工接管演示与尚未验收的自动模型客服。

## S2：单店自托管 MVP

**目标：** 让一家店在真实 Windows 等个人电脑或受控服务器上安装运行，自行录入并审核商品、销售政策和适用的平台规则，使用本地 Ollama 或现有云端 Provider 完成最小真实闭环。

**验收流程：**

1. 从新环境安装项目、依赖并配置私有管理员凭据；清楚记录需要的权限、下载和故障处理。
2. 商家录入并人工审核少量商品、价格、适用条件、发货说明、售后政策及 FAQ。
3. 商家为目标平台维护有来源、版本/生效时间和适用范围的平台规则；规则内容经审核后启用。系统应能对明确禁止的回复阻止发送并转人工，对条件不明的规则要求人工确认。
4. 使用真实模型请求验证商品知识内回答有依据；未覆盖的问题拒绝编造并进入人工接管。
5. 使用规则测试样例验证禁用、条件性及普通词语在上下文中的处理，避免把简单关键词命中误当成合规判断。此项只验证商家配置的规则范围，不宣称保证平台合规。
6. 停止或断开模型，验证访客明确看到不可用状态并能转人工。
7. 重启 API 和工作台，确认商品、知识、规则版本、会话与人工处理记录按预期持久化。
8. 留存脱敏的模型名、真实请求/响应、耗时、规则命中原因、错误和 PASS/FAIL/BLOCKED 结果；不能用 Mock 或 Codex 辅助回复冒充模型验收。

**发布门槛：** 只有配置好的真实模型在端到端测试中通过，才可宣称自动 AI 客服在已验证的范围内可用。单纯有 Provider 代码、状态页显示已配置、离线测试通过或演示中由人工回复，都不满足该门槛。

**可用性优先级：** 优先改善安装、配置检查、商家资料维护与审核、错误说明、数据备份/恢复和重启验证，降低普通用户部署阻力；先让一家店可靠跑通，不以新增功能数量作为进度目标。首个闭环只做售前商品咨询、规则检查和人工接管，不接真实支付、订单变更或自动发货。未证明可维护之前，不扩大部署范围。

## S3：真实用户试用

**目标：** 邀请 1–3 位商家，以经审核、授权且适当脱敏的商品和经营规则进行小范围试用。

**观察指标：**

- 重复咨询处理时间的变化（先定义一致的测量方式，不预设一定节省时间）。
- 商品/政策回答的准确性、无依据回答和人工修正情况。
- 人工接管的比例、原因、处理耗时和队列可用性。
- 安装配置障碍、设备资源、调用费用、隐私顾虑及商家持续使用意愿。

先获得商家和参与者许可，限定试用范围，避免输入支付凭据、身份证件或无关客户资料。记录真实结果，不预先填写用户数量以外的商业成果，不据小样本夸大准确率或销售收益。根据反馈决定是否值得继续，以及后续是否开发网页嵌入、更多模型 Provider，或经授权的第三方渠道集成。

## 首批明确排除

- 自动交易、订单创建或修改、改价、付款、退款和优惠承诺。
- 一次性接入所有电商、社交或消息平台。
- 多租户 SaaS、复杂组织权限体系和大规模部署架构。
- 没有商家审核依据的自动承诺或对商品、政策、库存、订单的猜测。

这些范围只有在真实用户需求、安全边界、权限控制和维护成本明确后，才另行讨论。任何可能改变价格、付款、退款、订单或客户数据的操作都不能仅由模型决定。

## 当前状态与推进原则

本仓库已有商品/知识管理、网站访客文字会话、SQLite 记录、人工接管、Streamlit 后台及销售训练基础。Windows runner 已验证模型关闭情况下的首次安装与启动；这不等于用户本机真实模型验收。Ollama 与 DeepSeek 配置路径不等于真实模型验收；自动 AI 客服、商家从录入到规则审核的完整自助体验、平台规则发送前拦截、长期公网服务和第三方电商接入目前均未完成相应验收。见 [README](../README.md)、[单店商品销售与客服 MVP 需求](STORE_SALES_MVP_REQUIREMENTS_ZH.md)、[本地模型部署说明](LOCAL_MODEL_DEPLOYMENT.md) 与 [部署边界](DEPLOYMENT.md)。

阶段完成必须由可重复的操作和真实证据支持。失败或前置条件不足时如实记录 FAIL 或 BLOCKED，先解决用户实际遇到的部署问题；不自行扩大范围、不以功能清单替代验收。
